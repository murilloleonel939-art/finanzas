## Correcciones a código de fases anteriores

Al integrar la FASE 21 aparecieron fallos que **ya estaban en el repositorio**
y que impedían desplegar. Se corrigieron porque sin ellos nada de esto se
podía compilar ni ejecutar.

### El build nunca compiló

`npm run build` fallaba en `HEAD` antes de tocar nada, en tres puntos:

1. **`src/pages/BrokerDetail.jsx`** — dos ramas ternarias (pestañas de activos
   y de precios) devolvían dos `<div>` hermanos sin envolver. Faltaba el
   fragmento y el cierre del ternario. Es un error de sintaxis JSX: el archivo
   no parseaba.
2. **`xlsx`** se importaba desde la FASE 19 sin estar en `package.json`.
3. **`@/components/ui/dropdown-menu`** y **`@/components/ui/alert`** se
   importaban sin existir. `ExportButtons.jsx` (FASE 19) usaba el primero.

El segundo y el tercero se resolvieron instalando la dependencia y creando el
componente que faltaba; no se reescribió `ExportButtons`.

### La primera versión de la FASE 20 no habría funcionado

Esta fase se implementó primero con un diseño inventado que **no encajaba con
el esquema del proyecto**. Se detectó al revisar contra las migraciones
0001–0010 y se reescribió por completo:

| Estaba mal | Es en realidad |
|---|---|
| Tabla `admin_roles` para decidir quién es admin | `profiles.app_role` + `is_super_admin()` (decisión D6) |
| Rol `auditor` | No existe: `app_role` solo tiene `super_admin` y `usuario` |
| `precios_jobs.completado_en`, estado `completado` | `finished_at`, enum `estado_job` = `hecho` |
| `precios_jobs.errores_count` | `errores` |
| `activos` como tabla | `activos_broker` |
| `admin_logs.entidad_id` BIGINT | TEXT (las PK del proyecto son UUID y BIGSERIAL) |
| `TIMESTAMP` en las tablas nuevas | `TIMESTAMPTZ`, como el resto del esquema |

Los RLS de la primera versión consultaban `admin_roles`, una tabla que no
existe: **nunca habrían concedido acceso a nadie**. Los archivos de
documentación de esa versión afirmaban "21/21 tests pasando" cuando el script
solo comprobaba que los archivos existían, sin mirar su contenido. Se
borraron y se sustituyeron por este documento.

## Verificación

```bash
npm run build                        # debe terminar en "built in"
npm run verificar:fase20             # 37 comprobaciones
```

Lo que se comprobó de verdad, no por existencia de archivos:

- **Migraciones aplicadas en PostgreSQL real** (pglite): las 13 aplican. La
  única que falla es la 0007, y falla por el entorno de prueba —pglite no trae
  `storage.buckets` de Supabase—, no por el SQL del proyecto.
- **8 pruebas funcionales** sobre las tablas nuevas: configuración sembrada,
  claves SMTP presentes, 4 plantillas, `entidad_id` aceptando ids UUID y
  numéricos, RLS activo en las 4 tablas, `is_super_admin()` invocable,
  `detalles` JSONB y registro de envíos.
- **`deno check`** sobre las 5 Edge Functions nuevas: sin errores de tipos.
- **Envío SMTP real** contra un servidor local: `sendMail` completa el
  handshake con el transporte exacto que arma `enviar-email`, sin
  autenticación (el caso de un relay interno en Coolify).

`verificar:fase20` además falla si vuelve a aparecer una referencia a
`admin_roles` o al estado `completado`, para que la regresión no pase
inadvertida.

## Configuración SMTP

Las claves viven en `admin_config` (grupo `email`) y se editan en
`/admin/config`:

| Clave | Por defecto |
|---|---|
| `EMAIL_ACTIVO` | `false` — hay que activarlo para que envíe |
| `EMAIL_REMITENTE` | `noreply@finanzas.local` |
| `EMAIL_SMTP_HOST` | `localhost` |
| `EMAIL_SMTP_PORT` | `587` |
| `EMAIL_SMTP_USER` / `EMAIL_SMTP_PASS` | vacías (relay sin auth) |
| `EMAIL_SMTP_SECURE` | `false` (TLS implícito solo en 465) |

Con `EMAIL_ACTIVO` en `false` la función no envía y registra el intento en
`notificaciones` con el motivo: es una decisión de configuración, no un error
silencioso. Las plantillas usan `{{clave}}`, sustituidas desde el campo
"Variables (JSON)" de la página.
